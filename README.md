# swift-serializer

Use this package to write typed values into a buffer by composing serializers. Start from `Serializing`: implement `serialize(_:into:)` for a leaf, or give the conformer a `body` built with `Builder` for a composite. Use `Serializer<Output, Buffer, Failure>` to wrap a closure or a builder block. The output may be noncopyable or nonescapable and is only borrowed, the buffer may be noncopyable, and every failure is typed. To read values in, use the sibling package swift-parser instead. To parse and serialize from one definition, use swift-coder. For exact byte layouts such as endianness, LEB128 or Base 64, use swift-binary.

## Laws

- Serializing only appends. No serializer clears, replaces or rewinds the buffer, and no combinator rolls back on failure: what earlier stages wrote stays in the buffer, and no stage after the failure runs. A failed serializer stays usable for the next call.
- The builder block passed to `Serializer<Output, Buffer, Failure>` runs once, at construction, and every call reuses the composition it built. A builder `if`/`else` is decided at that moment, and later changes to the condition have no effect.
- `Pair.Serializer<Failure>`, which backs each further line of a builder block, writes its first half before its second. A failure carries its provenance: the first half's failure on the left of the `Either`, the second's on the right. When both halves fail with the same type, the failure is that type and provenance is not kept. `Either.Serializer` likewise places the left branch's failure on the left and the right branch's on the right, whatever their types.
- `Map.Serializer<Upstream>` runs its transform before the upstream. When the transform fails, nothing is written and the upstream is not called. A throwing transform over a fallible upstream puts the upstream's failure on the left and the transform's on the right. `Map.Error.Serializer<Upstream>` calls its transform only when the upstream fails, once per failure, and leaves successful writes untouched.
- `Lazy.Serializer<Failure>` caches nothing. Every call runs the factory, uses the fresh serializer once and destroys it. When the factory fails, nothing is written, the failure is on the left, and the next call runs the factory again.
- `Repetition.Serializer` and `Repetition.Serializer.Separated<Separator>` check the bounds against the element count before writing anything, and empty bounds reject every output, the empty array included. Bounds are checked on every call, not at construction. Elements are written in array order. The separator is written only between elements, never before the first or after the last, so an empty or single-element output writes none. Element failures are on the left of the inner `Either` and separator failures on the right.
- `Swift.Optional.Serializer` writes nothing for `nil` and propagates a present value's failure. `Tagged.Serializer<Upstream>` writes exactly what its upstream writes for the underlying value. `Always.Serializer<Buffer>` writes nothing, whatever its value and the output.
- `Swift.Array.Serializer<Buffer>` and `Serializer::Literal<Buffer>` ignore the output and append their stored elements. A `Serializer::Literal<Buffer>` built from a string holds its UTF-8 bytes.
- `serialize(_:)` without a buffer starts from an empty `Buffer()` and returns it only when serializing succeeds.
